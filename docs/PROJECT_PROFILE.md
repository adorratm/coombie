## 3. Runtime architecture & entry points

### Confirmed playable path (solo survivor-like)

```
yarn dev:game
  → Vite :5173
  → index.html
  → preview.ts
  → createArena(#app)   [arena.ts]
  → rAF loop in preview.ts (HUD) + internal arena tick/render
```

Evidence: `apps/game-client/package.json` `dev`, `index.html` script tag, `preview.ts`.

### Alternate embeds

- `apps/web/src/app/arena/page.tsx` imports `createArena` from `@protocol-z/game-client` and drives HUD via React state.
- `apps/desktop` Electron window loads `PROTOCOL_Z_WEB_URL` (default `http://localhost:3000`) — **not** a native Steam build yet (`build` script is a placeholder echo).

### Simulation authority (current)

**Confirmed:** Combat, XP, spawns, damage, upgrades run **client-side** inside `createArena` (local progress state).  
**Confirmed:** `socket.io-client` is listed on `game-client` but **arena gameplay path does not drive match sync** (no Socket usage found in `arena.ts`).  
**Confirmed:** Nest match/lobby gateways + `game-engine` `createMatch` exist for a **future/partial** multiplayer layer; they are **not** the current solo play loop.

### Rendering & animation architecture

- Three.js scene + perspective camera + directional shadows (`shadowMap.autoUpdate = false` — manual/perf conscious).
- Operatives/zombies: optional procedural proxy mesh; preferred path loads **VRM** into hand/bones.
- Animation = **procedural Euler damping** on VRM humanoid bones (`dampBone` / grip poses / zombie attack poses) — **not** clip playback.
- Weapons: procedural `THREE.Mesh` groups parented to hand; muzzle aim via local +Z alignment.

### Physics

- Movement: discrete steps + `resolveCircleAabbs` against map colliders.
- Hits: distance / arc tests and projectile life (no rigid-body solver).

## 4. Current gameplay loop (implemented)

**Boot → combat → XP draft → scale → death/continue elements** (as coded in `arena.ts` / `preview.ts`):

1. **Boot:** Arena scene, player = roster `ironclad`, VRM preload/attach, weapon sync to progress unlocks.
2. **Combat:** Auto-aim nearest zombie in range; firearms spawn bullets; melee does arc damage; class ability on hotkey.
3. **Horde:** Timed spawn budget; kinds `grunt` | `acid` | `boss` (client); cap `MAX_ZOMBIES = 36`.
4. **Enemy skills:** Attack animation cycle + impact skills (spit/slam/roar/lunge/claw) via `zombieCombat.ts`.
5. **XP / level-up:** Gems → `gainProgressXp` → pending card choices; DOM upgrade overlay (reroll/lock/banish/skip).
6. **Meta-ish in-run:** Skill tree + inventory toggles; rescue slots grow squad up to `MAX_SQUAD_SIZE` (8).
7. **Mission HUD:** Chapter/sector objectives via `mission.ts` (overlay data).
8. **Failure:** Operative HP / death paths exist; full Steam “results + permanent meta” loop **not verified** as complete product UX.

Design doc aspirations (co-op 2–4, elite every 5 levels, Horde every 10, 8 named kit identities matching `GAME_DESIGN.md`) are **only partially** reflected in the live client (see gaps below).

## 9. Performance baseline & risks

| Item | Evidence / note |
|------|-----------------|
| Soft enemy cap | `MAX_ZOMBIES = 48` in `arena.ts` (was 36; spatial hash + VRM LOD) |
| Design aspiration | Docs/skills mention 500–1000 enemies — **not** current runtime |
| VRM cost | Distance LOD (`vrmLod.ts`): near full / mid alternate / far reduced-skip |
| Bullets × zombies | `SpatialHash2D` cell query (`spatialHash.ts`) before precise hit test |
| Shadows | Enabled; `autoUpdate = false` (good), still GPU cost when updated |
| Pixel ratio | Capped at `1.25` |
| Profiling harness | **No** in-repo FPS/profiler tooling found |
| Measured frame times | **Unknown** (not instrumented in audit) |

### High-risk hotspots (likely)

1. Scaling toward 100+ still needs pooling/instancing (LOD+hash only softens to ~48).  
2. Projectile–enemy uses spatial hash — still rebuilds grid 2×/frame.  
3. Large VRM downloads (~12–20 MB each) on first load.  
4. Dual UI paths (Vite HTML HUD vs Next arena page) increasing maintenance cost.
